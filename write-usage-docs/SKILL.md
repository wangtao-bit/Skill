# 技术使用说明编写规则

目标：让第一次使用的人能按文档从准备走到结果。以简短、可核对的操作步骤为主，不把使用说明写成设计文档。语言、术语与项目约定一致；没有约定时，跟随用户语言。

## 先核对，再写

- 明确读者要完成的任务、起始状态、运行环境与成功标准。先看项目约定及当前说明，再核对实际入口、参数解析、配置和对应测试；不要凭文件名或旧注释推断功能。
- 分清命令在哪台机器、哪个目录、哪个终端执行。多环境场景明确本机、远端、仿真和实机的差别；只写当前任务需要的依赖。
- 编辑已有文档时，沿用现有标题、术语和布局，只改受影响的内容。已有权威细节用相对链接引用，不维护多份相同说明。
- 仅写文档不擅自改代码、配置或执行会启动设备、覆盖文件、发布消息的命令。未实跑的命令不得写成已实测。

## 按操作者的顺序写

1. **标题指明模块或任务**：短标题，例如「航点巡检使用说明」。如果读者从标题就能明白用途，不必另写概述。
2. **准备 / 构建**：先写工作目录、依赖、构建和环境加载。常规步骤把可以在同一终端连续执行的命令放在同一个代码块。
3. **采集 / 配置**（需要才写）：把启动依赖、设备状态等前置条件放在命令之前。给一个最小可用命令，紧接着解释交互按键、确认、撤销、保存、输入输出路径，以及何时允许覆盖。
4. **执行**：使用上一步生成的文件或明确指出替代输入。说明服务或网络依赖，任务如何推进、失败是停止还是继续，以及结果保存位置和格式。
5. **可选说明**：只有确有需要时补参数、故障排查或进阶用法；正文保留完成任务的最短路径。

不强制使用「采集」这样的标题：部署工具、转换工具等用其真实步骤命名。不要为了套模板添加空节。

## 命令和措辞

- 代码块标注 `bash` 等语言，不带 `$` 提示符。长命令可续行，每个必需参数都出现在可复制示例里；解释写在代码块外。
- 区分普通 CLI 参数、框架参数、环境变量和配置字段，使用实现接受的确切拼写。说明有意义且已核对的默认值、单位、约束；不要把示例值写成默认值。
- 跨步骤复用同一示例文件名，标明哪些路径、话题或服务名需替换。不要在全局规则中写死某个项目的路径，也不要写凭据。
- 每个操作段优先采用「前置条件 → 命令 → 怎样操作 → 可观察结果 / 失败行为」。不要只写「成功后继续」，要说明成功后会发生什么。
- 在危险操作之前提示覆盖、设备运动或其他副作用，使用项目支持的显式确认选项，不把危险选项放进普通入门示例。
- 默认用短句和少量列表。常用参数直接放进对应步骤，避免为少量参数另建长表。

## 最小结构示例

```markdown
# <模块> 使用说明

## 构建
<在何处执行；构建及加载环境的命令>

## 采集输入
<前置条件；采集命令；确认、撤销、保存和覆盖规则>

## 执行任务
<使用上一步生成的输入；执行命令；成功推进、失败行为与结果文件>
```

## 交付前自检

- [ ] 命令、参数名和行为与当前入口一致；示例没有依赖未交代的默认值。
- [ ] 执行顺序完整；上一步的产物能作为下一步输入。
- [ ] 读者知道何时安全执行、如何确认成功、失败时会发生什么、结果去哪找。
- [ ] 没把本地源码核对、构建、自动化测试或实机运行混称为同一种验证。
- [ ] 仅修改所需文档，未覆盖其他人的内容或重复已有权威说明。
